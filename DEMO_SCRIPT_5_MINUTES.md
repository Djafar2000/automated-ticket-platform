# 5-Minute Demo Script

## Opening

Hello, my name is Djafar Aitseguer, and this is my Final Year Project build submission, called the **Automated Ticket Purchasing Platform**.

The purpose of this project is to address a real problem in high-demand ticket sales. Genuine users often miss out on tickets because the process is fast, stressful, and vulnerable to unfair automated behaviour. My project explores a more responsible alternative by combining user support, session monitoring, and administrative oversight in one platform.

For this demo, I will show the working prototype running end-to-end.

## Step 1: Show the Login Page

I am starting on the login page of the browser demo.

This version is designed as a reliable assessment build, so it can run locally without external dependencies. The main goal is to demonstrate the core project idea clearly and consistently.

On this page, a user can either register or log in. This supports the first core requirement of the system: user account access.

## Step 2: Register a User

I will create a new account now.

I enter a username, for example `djafar`, and a password such as `demo123`, then I click **Register**.

The system confirms that the account has been created successfully. In this demo version, the first created user is also treated as an admin, which helps demonstrate both the user and administrative sides of the platform in one recording.

## Step 3: Log In

Now I log in using the same credentials.

Once I click **Log In**, the system moves to the dashboard. This shows that the first meaningful part of the platform already works end-to-end: account creation and access into the system.

## Step 4: Explain the Dashboard

This is the main user dashboard.

At the top, the user can see the current account, the most recent session, and the latest result. The purpose of this screen is to give the user one place to configure a ticket attempt and understand what the platform is doing.

This reflects one of the major design decisions in the project: the platform should not behave like an opaque standalone bot. Instead, the user should be able to see progress, outcomes, and system state clearly.

## Step 5: Save Ticket Preferences

Next, I will complete the ticket preference form.

For this example:

- Event name: `Champions League Final`
- Seat type: `Standard`
- Quantity: `2`
- Budget cap: `180`

I click **Save Preferences**.

The system confirms that the preferences have been saved. This demonstrates the configuration feature of the platform and shows how a user can prepare for a future purchase attempt in advance.

## Step 6: Start a Purchase Session

Now I click **Start Purchase Session**.

This is the main end-to-end feature of the build. The system begins a simulated ticket-purchase workflow and updates the live status panel as it moves through the stages.

We can see the timeline changing through steps such as:

- preferences loaded
- searching the supported ticket flow
- queue waiting
- attempting reservation
- success

This is important because it demonstrates the core behaviour of the project: not just launching a process, but showing the user exactly what stage the system is in.

## Step 7: Show the Result and Transaction History

Once the session completes, the dashboard updates the last result and the transaction history table.

Here we can see the new transaction entry, including:

- transaction ID
- event
- seat type
- quantity
- status
- time

This shows that the system records the outcome of the purchase attempt and gives the user a visible history rather than a one-time action with no traceability.

## Step 8: Move to the Admin View

Now I switch to the **Admin** view.

This is an important part of the project because one of the key ideas behind this platform is that automation should be monitored and accountable.

On the admin dashboard, we can see:

- the number of registered users
- the number of sessions
- the number of alerts
- recent sessions
- recent transactions
- alert messages generated by the session flow

For example, the queue-handling alert demonstrates how the system can surface notable events during a purchase attempt.

This supports the project's value proposition: the system is not only helping the user, but also making session activity visible and reviewable from an administrative perspective.

## Step 9: Summarise What Works

So, in this build, the meaningful feature that works end-to-end is:

**registering and logging in, saving ticket preferences, launching a purchase session, tracking live status, storing the result, and reviewing it in the admin dashboard.**

That is the minimum version that proves the project idea in a practical and testable way.

## Step 10: Honest Limitations

There are also some important limitations to acknowledge.

This build uses a simulated purchase flow rather than a live ticketing website. It does not connect to real payment systems, real queues, or real CAPTCHA handling. Those areas were intentionally simplified so the prototype could remain reliable, demonstrable, and suitable for assessment.

The original Flask codebase is still included in the project folder, but this browser demo is the recommended assessment snapshot because it runs consistently without external setup.

## Closing

To conclude, this prototype demonstrates the core concept of my Final Year Project: a monitored ticket-purchasing platform that supports legitimate users while also providing transparency and oversight.

Thank you for watching.
